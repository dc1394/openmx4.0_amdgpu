Primary goal
============
Add experimental AMD GPU / ROCm / HIP optimized selected-eigensolver routines to MAGMA by applying Ozaki Scheme II through GEMMul8 to the BLAS-3 / BLAS-like matrix update phases of MAGMA’s existing selected symmetric/Hermitian eigensolver path.

The target is NOT the full-spectrum Xsyevd/Xheevd driver first.

The target is the selected-eigenpair family:
- real symmetric selected EVD:
  - magma_ssyevdx_ozaki2
  - magma_dsyevdx_ozaki2
  - magma_ssyevdx_ozaki2_gpu
  - magma_dsyevdx_ozaki2_gpu

- complex Hermitian selected EVD:
  - magma_cheevdx_ozaki2
  - magma_zheevdx_ozaki2
  - magma_cheevdx_ozaki2_gpu
  - magma_zheevdx_ozaki2_gpu

The main performance target is:
- AMD Instinct GPUs through ROCm/HIP,
- MAGMA’s HIP implementation as the baseline,
- selected eigenvalues/eigenvectors requested by index range:
  - range = MagmaRangeI
  - il, iu specify the selected eigenvalue index range
  - number of requested eigenpairs k = iu - il + 1
  - output m or mout must match existing MAGMA semantics.

Important AMD-specific premise
==============================
On the intended AMD GPU workloads, MAGMA’s selected eigensolver path is already the primary baseline and should not be replaced by hipSOLVER.

Do NOT implement this by calling hipSOLVER.

hipSOLVER may be used only as an optional benchmark/reference comparison when explicitly requested by a test driver. The implementation itself must preserve and extend MAGMA’s HIP eigensolver path.

Important mathematical interpretation
=====================================
Ozaki Scheme II is a high-precision GEMM / BLAS-like matrix product emulation technique. It is not a standalone symmetric/Hermitian eigensolver.

Therefore:
- preserve MAGMA’s existing selected eigensolver structure,
- preserve the tridiagonal reduction / selected tridiagonal eigensolve / eigenvector backtransform structure,
- apply GEMMul8 only to BLAS-3 or BLAS-like operations where it is mathematically correct and supported,
- do not replace scalar Householder logic, tridiagonal eigensolver logic, sorting logic, or LAPACK-style selected-eigenvalue logic with invented algorithms.

Critical selected-eigenpair requirement
=======================================
This work must optimize the selected-eigenpair case, especially:

    jobz  = MagmaVec
    range = MagmaRangeI
    il, iu chosen so that k = iu - il + 1 << n

Do not accidentally optimize only the all-eigenpair case.

When only k eigenvectors are requested:
- keep all public output semantics identical to MAGMA’s existing xSYEVDX/xHEEVDX routines,
- return only the requested m or mout eigenvalues/eigenvectors,
- ensure eigenvectors occupy the first m or mout columns, exactly as the existing MAGMA GPU selected-eigensolver API specifies,
- avoid expanding selected eigenvector operations to full n-by-n work unless MAGMA’s existing algorithm fundamentally requires it,
- where possible, apply accumulated orthogonal/unitary transformations to an n-by-k eigenvector matrix rather than an n-by-n matrix,
- route large n-by-k GEMM/TRMM-like backtransform operations through GEMMul8 when k is large enough to amortize overhead,
- fall back to native MAGMA/hipBLAS for very small k when GEMMul8 overhead is likely to dominate.

Candidate operations to route through GEMMul8
=============================================
After inspecting the selected eigensolver call graph, route only supported BLAS-like operations through GEMMul8.

Likely candidates:
- GEMM
- SYMM / HEMM
- SYRK / HERK
- SYR2K / HER2K
- TRMM
- TRSM
- any supported GEMMul8 operation actually used in MAGMA’s selected-eigensolver reduction or eigenvector backtransform path

Pay special attention to selected eigenvector backtransform:
- operations of shape n-by-k, panel-by-k, or block-by-k are central when k = iu - il + 1,
- do not force full n-by-n GEMM when an n-by-k update is sufficient,
- benchmark GEMMul8 thresholds separately for k = 1, 2, 4, 8, 16, 32, 64, n/10, n/2, n.

Do not route unsupported operations:
- SYMV / HEMV
- GEMV
- scalar Householder updates
- tridiagonal eigensolver kernels
- CPU LAPACK calls
- index selection / eigenvalue sorting logic
unless GEMMul8 explicitly supports them and the substitution is mathematically identical.

Implementation strategy
=======================
1. Start from MAGMA’s existing selected eigensolver code.

Do not write a new eigensolver from scratch.

Create _ozaki2 wrappers and internal variants by:
- reusing existing argument validation,
- reusing workspace query logic,
- reusing matrix scaling/rescaling logic,
- reusing tridiagonal selected eigensolver logic,
- reusing eigenvalue sorting semantics,
- reusing INFO semantics.

2. Identify selected-eigenvector matrix dimensions.

For each BLAS-like operation in the selected-eigenvector path, document:
- operation name,
- source file,
- matrix dimensions,
- whether dimensions depend on k = iu - il + 1,
- whether it runs on GPU,
- whether GEMMul8 supports it,
- whether it is safe to replace.

3. Add Ozaki-II versions only where useful.

Possible internal variants:
- dsytrd_ozaki2 / ssytrd_ozaki2
- zhetrd_ozaki2 / chetrd_ozaki2
- dormtr_ozaki2 / sormtr_ozaki2
- zunmtr_ozaki2 / cunmtr_ozaki2
- selected backtransform helpers that explicitly operate on n-by-k matrices

Create these only if they map to real internal MAGMA routines.

4. Preserve selected output semantics.

For range = MagmaRangeI:
- validate il and iu exactly as MAGMA currently does,
- k = iu - il + 1,
- output m or mout must equal k on success,
- w[0:k-1] contains requested eigenvalues in ascending order,
- if jobz = MagmaVec:
  - A or dA first k columns contain the requested eigenvectors,
  - columns beyond k must not be treated as valid output,
  - do not overwrite output layout relative to the existing MAGMA API.

For range = MagmaRangeV:
- preserve existing behavior,
- m or mout is determined by eigenvalues in (vl, vu],
- support Ozaki-II where safe,
- do not prioritize this over MagmaRangeI.

For range = MagmaRangeAll:
- behavior should match existing xSYEVDX/xHEEVDX all-eigenpair behavior,
- but this is not the main optimization target.

5. Avoid full-spectrum work where possible.

When jobz = MagmaVec and range = MagmaRangeI:
- avoid computing all eigenvectors if MAGMA already has a selected-vector path,
- if existing MAGMA code internally forms all eigenvectors, investigate whether the backtransform can be restricted to selected columns,
- do not make risky algorithmic changes without tests,
- if full-vector formation is unavoidable, document exactly why.

Accuracy checks
===============
For real symmetric:
- compare eigenvalues against LAPACK or existing MAGMA selected eigensolver
- residual for selected eigenpairs:
  ||A_original * V_k - V_k * diag(w_k)|| / (||A_original|| * n * eps)
- orthogonality:
  ||I_k - V_k^T V_k|| / (k * eps)

For complex Hermitian:
- compare eigenvalues against LAPACK or existing MAGMA selected eigensolver
- residual:
  ||A_original * V_k - V_k * diag(w_k)|| / (||A_original|| * n * eps)
- orthogonality:
  ||I_k - V_k^H V_k|| / (k * eps)

For jobz = MagmaNoVec:
- compare selected eigenvalues only.

The tests must verify that only the first k columns are interpreted as selected eigenvectors.
